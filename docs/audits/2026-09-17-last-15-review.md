# Review of the last 15 commits — 2026-09-17

Reviewed `2ff45b01..004ef27c` against the baseline `2ff45b01`. The batch cannot
be signed off as fully correct: it contains three reproduced regressions and
two incomplete fixes. No compiler or library implementation was changed during
this review. The findings are tracked as BUG-367 through BUG-371 in BUGS.md.

## Findings

### P1 — by-value parameter cleanup double-frees heap ownership (BUG-367)

Commit `c5911822` registers each owning parameter for destruction without
changing the shallow copy at the call site or transferring the caller's
ownership. Both copies free the same allocation.

```bpl
extern malloc(size: long) ret *void;
extern free(ptr: *void) ret void;
extern printf(fmt: string, ...) ret int;

struct Resource {
    data: *void,
    @[auto_destroy]
    frame destroy(this: *Resource) ret void { free(this.data); }
}

frame use(r: Resource) ret void { printf("%p\n", r.data); }

frame main() ret int {
    local r: Resource = Resource { data: malloc(16) };
    use(r);
    return 0;
}
```

At the baseline this exits successfully at O0 and O3. At the reviewed head it
aborts with a double free at both levels; AddressSanitizer independently reports
`attempting double-free` at both levels. Printing the pointer makes the
allocation observable: an empty `use` can let O3 eliminate the allocation and
mask the bug. Existing tests print destruction counters rather than freeing
owned allocations, so they accept duplicated resource ownership.

Fix ownership transfer/copy validation and cleanup together. Removing parameter
cleanup alone would reintroduce leaks for owning temporaries passed directly to
a function. A conservative safety fix can reject unsupported ownership copies;
full move semantics require tracking the moved source and subsequent uses.
Until then, pass a pointer and retain one owner. This problem also matters when
copying owners into locals, tuples, and fields.

### P1 — enum ownership rejection misses aliases and generics (BUG-368)

Commit `bffa7fe1` walks raw struct field declarations at enum declaration time.
It neither resolves aliases nor substitutes instantiated generic arguments.
Each of the following passes `check`, compiles at O0/O3, and skips cleanup.
Use this resource declaration with each independent case:

```bpl
extern printf(fmt: string, ...) ret int;
struct Resource {
    value: int,
    @[auto_destroy]
    frame destroy(this: *Resource) ret void { printf("destroy %d\n", this.value); }
}
```

Generic enum:

```bpl
enum Slot<T> { Has(T), Empty }
frame main() ret int {
    local _s: Slot<Resource> = Slot<Resource>.Has(Resource { value: 42 });
    return 0;
}
```

Generic wrapper:

```bpl
struct Box<T> { value: T }
enum Slot { Has(Box<Resource>), Empty }
frame main() ret int {
    local _s: Slot = Slot.Has(Box<Resource> { value: Resource { value: 42 } });
    return 0;
}
```

Alias:

```bpl
type R = Resource;
enum Slot { Has(R), Empty }
frame main() ret int {
    local _s: Slot = Slot.Has(Resource { value: 42 });
    return 0;
}
```

All three also leaked at the baseline, so this is an incomplete fix rather
than a newly introduced leak. Resolve aliases and concrete field types, and
validate generic enum instantiations as well as declarations. The destructor
guide's blanket claim that owning payloads are rejected is currently too broad.

### P1 — inherited spec methods retain unresolved generic types (BUG-370)

Commit `72d7ab70` finds the ancestor's method but builds its thunk using the
child's generic substitutions. A non-generic child of a concrete generic parent
already demonstrates the failure:

```bpl
extern printf(fmt: string, ...) ret int;
spec Value { frame get(this: *Self) ret int; }
struct Base<T>: Value {
    value: T,
    frame get(this: *Base<T>) ret int { return cast<int>(this.value); }
}
struct Child: Base<int> { tag: int }
frame use(v: *Value) ret int { return v.get(); }
frame main() ret int {
    local c: Child;
    c.value = 42;
    c.tag = 0;
    printf("%d\n", use(&c));
    return 0;
}
```

`check` succeeds, but native compilation at O0/O3 fails on undefined
`%struct.Base_T` in the generated thunk. A `Child<U>: Base<U>` instantiated as
`Child<int>` also fails, with an unresolved `%struct.Base_U`. Both programs
failed earlier in code generation at the baseline, so this is incomplete
generic support in the fix. Carry the concrete ancestor type and substitutions
through method lookup and use them for both the implementation signature and
symbol. Extend coverage beyond non-generic inheritance.

### P2 — returning an address into a borrowed slice is rejected (BUG-369)

Commit `93a113d4` treats slice indexing like storage inside a fixed array:

```bpl
frame first(xs: int[]) ret *int { return &xs[0]; }
frame main() ret int {
    local xs: int[2] = [0, 2];
    return *first(xs);
}
```

The baseline compiles and returns zero at O0/O3. The reviewed head rejects the
return as a pointer into `first`'s frame. The element actually belongs to the
caller's backing array; only the slice descriptor is in the callee. Stop the
storage walk at borrowed element access, while retaining rejection of addresses
inside local fixed arrays. This does not solve the separately documented lack
of pointer escape analysis.

### P2 — deferred writes through a slice are rejected (BUG-371)

Commit `315ff3d8` reuses capture analysis that recognizes pointer indirection but
not slice element indirection:

```bpl
extern printf(fmt: string, ...) ret int;
frame update(xs: int[]) { defer { xs[0] = 42; } }
frame main() ret int {
    local xs: int[1] = [0];
    update(xs);
    printf("%d\n", xs[0]);
    return 0;
}
```

The baseline prints `42` at O0/O3. The reviewed head rejects the assignment with
`BPL_CAPTURED_VALUE_ASSIGNED`, saying the write would be discarded. A captured
slice descriptor retains the backing pointer, so the write is observable. Treat
element writes through slices separately from rebinding captured descriptors
and from modifying captured fixed arrays. The shared helper also affects
lambda capture validation.

Two points from the review deserve recording beyond the fixes.

The double free was not merely a missed case. A callee cannot tell whether its
argument was a temporary it may consume or a copy the caller still owns, so
callee-side cleanup cannot be made correct on its own, and the change should
not have been made without that question answered. It is withheld rather than
patched, and its test is skipped with the reason attached.

The review's observation about the tests is the more important one: they print
destruction counters instead of releasing a resource, so a duplicated owner
reads as an extra line of output rather than a fault. That is why the defect
survived a full suite, two fuzz campaigns, and a sanitizer run. It also means
the ownership work rests on weaker evidence than the earlier audit claimed.

That test weakness exposed a defect wider than this batch, now tracked as
BUG-372: copying a value that owns a destructor duplicates ownership, so
`local copy: Resource = original;` frees the same allocation twice, and has
since before this work. The fix is to reject such copies, which also makes the
withheld parameter cleanup correct, because every by-value argument would then
be a transfer. That is a language change and is left for the maintainer to
decide; until it lands, `@[auto_destroy]` is only safe for values that are
never copied.
