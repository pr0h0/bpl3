### BUG-226: Switch fallthrough skips deferred cleanup (P1)

**Source:** [compiler/backend/codegen/StatementGenerator.ts:2514](../../compiler/backend/codegen/StatementGenerator.ts#L2514).

**Evidence:** Expected `one → cleanup → two → end`; actual `one → two → end`. No cleanup message is printed, even at function exit. LANGUAGE_SPEC.md:293 explicitly includes fallthrough among scope exits that execute defer.

**Cause:** generateFallthrough emits a branch without unwinding the case scope. The normal block cleanup is bypassed by the terminator.

**Suggested fix:** Emit cleanup for every scope exited by fallthrough before branching. Share scope-exit lowering with break, continue, return, and match yields; preserve LIFO order.

**Reproduction:** Save as `/tmp/bpl-audit-case.bpl`, then run from the repository root with `bun index.ts run /tmp/bpl-audit-case.bpl -O 0` and `-O 3`.

```bpl
extern printf(fmt: string, ...);
frame main() ret int { switch (1) { case 1: defer printf("cleanup\n"); printf("one\n"); fallthrough; case 2: printf("two\n"); break; } printf("end\n"); return 0; }
```

### BUG-227: Returning a match-arm value skips deferred cleanup (P1)

**Source:** [compiler/backend/codegen/StatementGenerator.ts:2138](../../compiler/backend/codegen/StatementGenerator.ts#L2138).

**Evidence:** Expected `cleanup` before `value=1`; actual output is only `value=1`. The arm return correctly yields to the match expression, but never executes the arm cleanup.

**Cause:** The !isMatchYield guard encloses all deferred cleanup. A match yield then branches directly to the merge block.

**Suggested fix:** Track the scope depth at match entry and unwind the scopes exited by a yield. Keep enclosing function cleanup pending.

**Reproduction:** Save as `/tmp/bpl-audit-case.bpl`, then run from the repository root with `bun index.ts run /tmp/bpl-audit-case.bpl -O 0` and `-O 3`.

```bpl
extern printf(fmt: string, ...);
frame main() ret int { local v: int = match (true) { true => { defer printf("cleanup\n"); return 1; }, false => 2, }; printf("value=%d\n", v); return 0; }
```

### BUG-228: A return in one branch suppresses destruction in another branch (P1)

**Source:** [compiler/backend/codegen/StatementGenerator.ts:2141](../../compiler/backend/codegen/StatementGenerator.ts#L2141).

**Evidence:** choose(false) returns resource 2 but fails to destroy resource 1. Expected `destroy 1 → chosen 2 → destroy 2`; actual `chosen 2 → destroy 2`. The reproduction uses logging destructors, with no resource allocation.

**Cause:** Generating the earlier return a inserts a into movedAutoDestroyAddresses, a mutable set shared across the rest of function generation. generateAutoDestroy at line 1497 consults that set on the later return b path, even though the earlier branch did not execute.

**Suggested fix:** Make the return-value cleanup exclusion local to each emitted exit, or introduce control-flow-aware move state with explicit branch merges. Test both flag values and nested branches.

**Reproduction:** Save as `/tmp/bpl-audit-case.bpl`, then run from the repository root with `bun index.ts run /tmp/bpl-audit-case.bpl -O 0` and `-O 3`.

```bpl
extern printf(fmt: string, ...);
struct Resource { id: int, @[auto_destroy] frame destroy(this: *Resource) { printf("destroy %d\n", this.id); } }
frame choose(flag: bool) ret Resource { local a: Resource = Resource { id: 1 }; local b: Resource = Resource { id: 2 }; if (flag) { return a; } return b; }
frame main() ret int { local r: Resource = choose(false); printf("chosen %d\n", r.id); return 0; }
```

### BUG-229: Default Map equality silently rejects supported-looking key types (P1)

**Source:** [lib/map.bpl:127](../../lib/map.bpl#L127).

**Evidence:** After set(true, 1), has(true) is false. Setting true again increments count to 2 instead of updating the existing entry. The generic constructor accepts Map<bool, int> without a diagnostic.

**Cause:** _mapDefaultEq falls through to false for bool, while _mapDefaultHash falls through to zero. Other types absent from the dispatch also lack defaults, but runtime validation here specifically covered bool.

**Suggested fix:** Define an explicit default-key capability, supply correct hash/equality for permitted keys, and reject unsupported default constructors at compile time. Keep the custom hasher/equaler overload available.

**Reproduction:** Save as `/tmp/bpl-audit-case.bpl`, then run from the repository root with `bun index.ts run /tmp/bpl-audit-case.bpl -O 0` and `-O 3`.

```bpl
import [Map] from "std/map.bpl"; extern printf(fmt: string, ...);
frame main() ret int { local m: Map<bool, int> = Map<bool, int>.new(); m.set(true, 1); printf("%d\n", m.has(true)); m.set(true, 2); printf("%d\n", m.count); return 0; }
```

### BUG-230: NaN inequality disagrees with negated equality (P2)

**Source:** [compiler/backend/codegen/BinaryExpressionGenerator.ts:1009](../../compiler/backend/codegen/BinaryExpressionGenerator.ts#L1009).

**Evidence:** For n = nan(""), printing n == n, n != n, !(n == n) produces `0 0 1`; expected ordinary floating-point inequality is `0 1 1`. This also breaks the familiar x != x NaN check.

**Cause:** Scalar != uses fcmp one, which requires both operands to be ordered. fcmp une includes unordered operands and is the complement of ordered equality.

**Suggested fix:** Use fcmp une for scalar floating-point != and lock down NaN behavior for scalar and aggregate comparisons. See [LLVM fcmp semantics](https://llvm.org/docs/LangRef.html#fcmp-instruction).

**Reproduction:** Save as `/tmp/bpl-audit-case.bpl`, then run from the repository root with `bun index.ts run /tmp/bpl-audit-case.bpl -O 0` and `-O 3`.

```bpl
extern printf(fmt: string, ...); extern nan(tag: string) ret float;
frame main() ret int { local n: float = nan(""); printf("%d %d %d\n", n == n, n != n, !(n == n)); return 0; }
```

### BUG-231: Floating-point unary minus loses negative zero (P2)

**Source:** [compiler/backend/codegen/UnaryExpressionGenerator.ts:149](../../compiler/backend/codegen/UnaryExpressionGenerator.ts#L149).

**Evidence:** With z = 0.0, copysign(1.0, -z) prints `1.0`, whereas sign-changing negation should produce `-1.0`.

**Cause:** Negation is emitted as fsub double 0.0, value. Subtracting positive zero from positive zero does not implement sign-bit negation.

**Suggested fix:** Use LLVM fneg for floating-point negation. It flips the sign bit and preserves the remaining representation. See [LLVM fneg semantics](https://llvm.org/docs/LangRef.html#fneg-instruction).

**Reproduction:** Save as `/tmp/bpl-audit-case.bpl`, then run from the repository root with `bun index.ts run /tmp/bpl-audit-case.bpl -O 0` and `-O 3`.

```bpl
extern printf(fmt: string, ...); extern copysign(x: float, y: float) ret float;
frame main() ret int { local z: float = 0.0; printf("%.1f\n", copysign(1.0, -z)); return 0; }
```

### BUG-232: f32 is recognized as a type but rejected as numeric (P2)

**Source:** [compiler/middleend/TypeUtils.ts:108](../../compiler/middleend/TypeUtils.ts#L108).

**Evidence:** A function returning -x for an f32 parameter is rejected with BPL_UNARY_NEGATION_OPERAND_TYPE_MISMATCH. A separate check of cast<f32>(1.5) fails with BPL_CAST_INVALID. docs/06-operators.md lists f32 and f64 among supported arithmetic types.

**Cause:** TypeUtils.isNumericType and NUMERIC_TYPES omit f32/f64, while TypeGenerator.ts:61 maps them to LLVM floating-point types and TypeCheckerBase.ts reserves them as builtins. Fixing the frontend alone is insufficient: the unary emitter also only special-cases double.

**Suggested fix:** Centralize builtin type definitions: category, width, signedness, canonical aliases, conversion rules, LLVM type, and debug metadata. Exercise all documented numeric spellings through arithmetic and conversions. Runtime reproduction here covers f32; f64 omission is source evidence.

**Reproduction:** Save as `/tmp/bpl-audit-case.bpl`, then run from the repository root with `bun index.ts run /tmp/bpl-audit-case.bpl -O 0` and `-O 3`.

```bpl
extern printf(fmt: string, ...); frame neg(x: f32) ret f32 { return -x; } frame main() ret int { local x: f32; local y: f32 = neg(x); return 0; }
```

### BUG-233: JSON Unicode escapes are silently decoded incorrectly (P2)

**Source:** [lib/json.bpl:144](../../lib/json.bpl#L144).

**Evidence:** Parsing the valid JSON string "\u0041" returns `u0041` rather than `A`, without reporting an error.

**Cause:** parseString handles short escapes but has no Unicode escape branch. The fallback copies the escape letter and subsequently treats the hexadecimal digits as ordinary text.

**Suggested fix:** Decode four-digit Unicode escapes, combine valid surrogate pairs, and encode the resulting code points consistently with the string representation. Reject invalid escapes instead of silently changing text. See [RFC 8259 section 7](https://www.rfc-editor.org/rfc/rfc8259#section-7).

**Reproduction:** Save as `/tmp/bpl-audit-case.bpl`, then run from the repository root with `bun index.ts run /tmp/bpl-audit-case.bpl -O 0` and `-O 3`.

```bpl
import [JSON] from "std/json.bpl"; extern printf(fmt: string, ...);
frame main() ret int { local s: *string = JSON.parse<string>("\"\\u0041\""); if (s != nullptr) { printf("%s\n", *s); } return 0; }
```

### BUG-235: Map bucket storage never scales with entry count (P2)

**Source:** [lib/map.bpl:171](../../lib/map.bpl#L171), [set at line 207](../../lib/map.bpl#L207).

**Source evidence:** The default constructor creates 16 buckets. set walks a bucket chain and links a node without a load-factor check or rehash. No growth path appears elsewhere in Map. With B fixed buckets, average chains grow with n/B; with the default B=16, lookup and insertion cannot remain expected O(1) as n grows. Bulk insertion can approach quadratic total work. This is an algorithmic inference from the implementation, not a measured runtime comparison. An attempted external bucket-count probe was rejected by member resolution and is not evidence for this finding.

**Suggested fix:** Grow and rehash on a bounded load factor, expose reserve, and benchmark successful/unsuccessful lookups and insertion at multiple sizes. State iterator/reference invalidation rules.

## What holds the language back

1. **Cleanup semantics lack a single implementation.** The three independent cleanup failures suggest a shared lowering step for exits, with the source and destination scope depth made explicit. Move handling must belong to a particular control-flow path. Establish copy, borrow, return-transfer, and destruction rules before building more ownership-sensitive abstractions.

2. **Compiler stages duplicate the type model.** f32 is one concrete consequence. Consolidate builtin metadata and canonicalization, then use typed operations for comparisons, casts, and arithmetic instead of independently maintained string-name lists. Preserve the current architecture incrementally rather than attempting a rewrite.

3. **The backend is difficult to reason about locally.** CodeGenerator reaches BaseCodeGenerator through thirteen inheritance steps; many emitters share mutable state and manually emit LLVM text. Introduce a small typed IR builder that validates instruction operands, blocks, and terminators, and pass explicit function/scope contexts to emitters. Start with the cleanup and numeric paths identified here.

4. **The standard library needs stronger behavioral contracts.** A generic map must either support a key type correctly or reject it. JSON needs a conformance corpus. Add laws such as set(k,v) implies has(k), replacement preserves size, parsing escaped text equals parsing its literal equivalent, and each scope exit runs its registered cleanup exactly once.

5. **Test combinations and expected semantics.** The existing 455 passing selected tests did not cover these cases. Add a matrix across scope-exit kind, nested blocks, conditional return paths, optimization level, and numeric type spelling. Extend seeded cases with explicit expected outputs, NaNs, signed zeros, and standard-library operations. Keep LLVM verification, but remember valid LLVM can still implement the wrong language behavior.

6. **Documentation promises need executable checks.** Synchronize README, LANGUAGE_SPEC, AGENTS.MD, and tutorials. README also presents broad zero-cost and null-safety claims while the documented language includes raw pointers and runtime checks. Describe exactly what is checked and what has measured zero overhead; avoid implying universal guarantees.

## Performance measurement

A small local compiler benchmark used `bun benchmark/measure_compilation.ts --mode phases --functions 1000 --rounds 5 --warmups 1 --json`. For the 194,977-character synthetic source and 53,086 tokens, median lex/parse/typecheck/codegen times were **7.34 / 21.74 / 31.72 / 34.00 ms**; the reported full-phase median was **93.26 ms**. Phase medians do not necessarily sum to the median total.

This short, warm synthetic measurement excludes native backend/linker timing and is not evidence that overall compilation is slow. Profile cold CLI startup, large import graphs, generic-heavy real programs, incremental rebuilds, and native linking before choosing compiler optimizations. The map growth issue is a more concrete scaling problem than a general claim about compiler speed.

## Suggested repair order

1. Add regression coverage for BUG-226–228, then unify cleanup and make move exclusions path-specific.
2. Correct default Map key handling and add growth/rehashing with size-sensitive benchmarks.
3. Centralize numeric type metadata; repair NaN comparison, signed-zero negation, and f32 operations.
4. Implement JSON Unicode escape decoding and add conformance tests.
5. Reconcile documentation and compile its examples in CI.
